디지털 증거는 사건과 관련된 사실을 확인하는 데 활용할 수 있는 디지털 형태의 정보다.

문서나 사진뿐 아니라 로그인 기록, 메시지, 네트워크 패킷, 파일 시스템 메타데이터도 디지털 증거가 될 수 있다.

분석해서 무엇을 찾았는지만큼, 그 데이터를 어떻게 확보하고 보존했는지가 중요하다.

```text
데이터 확보
-> 수집 경위 기록
-> 원본 보존과 무결성 확인
-> 작업 복사본 분석
-> 근거와 검증 결과 제시
```

앞선 [디지털 포렌식]({% post_url 2026-10-08-digital-forensics %})이 분석 과정과 분야를 다뤘다면, 이 글은 분석 대상인 증거의 특성과 관리 원칙을 정리한다.

---

## 디지털 데이터의 특성

디지털 데이터는 물리적인 물건과 다른 방식으로 저장되고 변경된다.

| 특성 | 설명 | 관련 쟁점 |
| --- | --- | --- |
| 비가시성 | 저장된 비트의 의미를 도구로 해석해야 한다 | 도구의 신뢰성, 분석자의 전문성 |
| 휘발성 | 전원 차단이나 시간 경과로 일부 데이터가 사라진다 | 수집 순서, 신속한 보존 |
| 변조 용이성 | 내용이나 기록을 수정하기 쉽고 일반적인 사용으로도 변경될 수 있다 | 무결성 검증, 변경 이력 |
| 복제 용이성 | 같은 바이트 내용을 가진 복사본을 만들 수 있다 | 원본과 복사본의 동일성 검증 |
| 대규모성 | 분석 대상의 양이 매우 클 수 있다 | 검색·선별 방법, 조사 범위와 개인정보 |
| 초국경성 | 여러 국가의 서버와 서비스에 분산될 수 있다 | 관할, 접근 권한, 서비스 사업자 협조 |

### 비가시성

파일이나 로그의 내용을 확인하려면 운영체제, 뷰어, 파서 등의 도구가 필요하다.

같은 데이터도 도구 설정이나 파서의 해석에 따라 다르게 표시될 수 있다. 분석 결과에는 원본 데이터의 위치와 사용 도구, 버전을 함께 기록한다.

### 휘발성

RAM에 있는 프로세스 정보와 연결 상태는 전원이 꺼지면 사라질 수 있다. 로그도 보존 기간이 지나거나 순환 기록으로 덮어쓰이면 없어질 수 있다.

모든 디지털 데이터가 같은 속도로 사라지는 것은 아니다. 휘발성과 수집 영향을 고려해 확보 순서를 정한다.

### 변조와 복제

디지털 파일은 쉽게 복사할 수 있지만, 복사 과정에서 파일 시스템의 시각 정보나 권한까지 동일하게 보존되는 것은 아니다.

파일 내용의 동일성과 주변 메타데이터의 보존 여부를 구분해야 한다.

### 대규모성과 초국경성

대용량 저장장치나 클라우드 계정에는 사건과 무관한 정보도 함께 들어 있다.

조사 질문에 맞는 범위를 정하고, 검색 조건과 선별 기준을 기록한다. 클라우드 데이터는 저장 위치와 서비스 구조에 따라 수집 권한과 절차도 달라질 수 있다.

## 증거능력과 증명력

`증거능력`은 법정에서 증거로 사용할 수 있는 자격을 뜻한다.

`증명력`은 그 증거가 사실을 얼마나 설득력 있게 뒷받침하는지를 뜻한다.

```text
증거능력: 증거로 사용할 수 있는가?
증명력: 무엇을 얼마나 뒷받침하는가?
```

예를 들어 해시가 일치하는 파일이라도, 수집 절차나 출처에 문제가 있으면 해시만으로 증거능력을 확보할 수 없다.

또한 로그인 기록이 증거로 사용될 수 있더라도 실제 사용자가 누구였는지는 다른 자료로 확인해야 할 수 있다.

## 디지털 증거의 관리·검증 원칙

사진의 다섯 항목은 증거를 신뢰할 수 있게 관리하고 설명하기 위한 원칙으로 정리할 수 있다.

모든 사건에 동일하게 적용되는 법정의 다섯 가지 독립 요건으로 단정하기보다는, 적법한 수집과 동일성·무결성을 뒷받침하는 관점으로 이해한다.

| 원칙 | 의미 | 남겨야 할 기록 |
| --- | --- | --- |
| 적법성 (Legality) | 권한과 절차에 맞게 증거를 수집하고 처리한다 | 수집 근거, 허용 범위, 수집 과정 |
| 무결성 (Integrity) | 증거 내용의 변경 여부를 확인하고 보존한다 | 해시, 검증 시각, 변경·오류 기록 |
| 재현성 (Reproducibility) | 같은 데이터와 조건에서 분석 결과를 검증할 수 있게 한다 | 도구·버전, 설정, 절차, 원본 위치 |
| 신속한 보존 (Preservation) | 사라질 수 있는 데이터를 적절한 시점에 확보한다 | 수집 우선순위, 시작·종료 시각 |
| 관리 연속성 (Chain of Custody) | 수집부터 제출까지 증거의 취급 이력을 추적한다 | 담당자, 전달 시각, 장소, 처리 목적 |

### 적법성

한국 형사절차에서 [형사소송법 제308조의2](https://law.go.kr/joStmdInfoP.do?joBrNo=02&joNo=0308&lsiSeq=242053)는 적법한 절차에 따르지 않고 수집한 증거를 증거로 사용할 수 없도록 규정한다.

수집 권한과 범위를 확인하고 그 근거를 기록해야 한다. 증거능력의 구체적인 판단에는 사건에 적용되는 법령과 판례, 증거의 성격이 함께 고려된다.

### 무결성

확보한 증거는 보존하고 분석은 작업 복사본에서 수행한다.

해시를 비교하면 같은 알고리즘으로 계산한 대상의 바이트 내용이 같은지 검증하는 데 도움이 된다.

라이브 수집처럼 변경을 완전히 피하기 어려운 작업은 도구 실행과 발생한 변경을 기록한다.

### 재현성

"분석 도구에서 발견했다"만으로는 결과를 검증하기 어렵다.

도구 이름과 버전, 입력 데이터, 실행 옵션, 시간대 설정, 추출 경로 등을 남겨 다른 분석자가 같은 조건으로 확인할 수 있게 한다.

### 신속한 보존

메모리나 단기 보존 로그는 수집이 늦어지면 사라질 수 있다.

신속성은 무조건 빨리 복사한다는 뜻이 아니다. 휘발성, 공격의 지속 여부, 수집으로 인한 영향을 고려해 필요한 데이터를 우선 확보한다.

### 관리 연속성

`Chain of Custody`는 증거를 누가, 언제, 어디서, 어떤 목적으로 취급했는지 이어서 기록하는 것이다.

```text
수집 담당자
-> 보관 담당자
-> 분석 담당자
-> 제출 담당자

각 단계의 인계·인수와 처리 내역 기록
```

해시만 남기고 관리 이력을 생략하면 증거의 출처와 전달 과정을 충분히 설명하기 어렵다.

## 해시 함수와 해시 값

`해시 함수`는 입력 데이터를 정해진 길이의 값으로 변환하는 함수다.

그 결과를 `해시 값`이라고 한다. 보고서에는 사람이 읽기 쉽도록 보통 16진수 문자열로 표시한다.

```text
파일의 바이트 데이터
-> SHA-256 계산
-> 256비트 해시 값
-> 64자리 16진수로 표시
```

같은 알고리즘에 같은 데이터를 입력하면 같은 값이 나온다. 입력 파일의 크기와 관계없이 출력 길이는 알고리즘에 따라 정해져 있다.

암호학적 해시는 입력이 조금만 달라져도 출력이 크게 달라지는 특성이 있다.

다만 서로 다른 입력이 같은 값으로 계산되는 `충돌`은 이론적으로 가능하다. "한 글자만 바뀌어도 반드시 다른 값이 나온다"는 절대적인 보장은 아니다.

또한 해시는 데이터를 암호화하는 기능이 아니다. 해시 값에서 원본 파일을 복원하는 용도로 사용하지 않는다.

---

## 해시 값이 중요한 이유

확보 직후 기록한 해시와 이후 계산한 해시를 비교하면 보존·복사 과정에서 내용이 달라졌는지 확인할 수 있다.

| 비교 결과 | 해석 |
| --- | --- |
| 같은 알고리즘과 같은 범위에서 해시 일치 | 바이트 내용의 동일성을 뒷받침한다 |
| 같은 알고리즘과 같은 범위에서 해시 불일치 | 바이트 내용이 다르므로 원인을 조사해야 한다 |
| 알고리즘 또는 계산 범위가 다름 | 동일성 비교의 기준으로 바로 사용할 수 없다 |

해시가 다르다는 사실만으로 고의적인 조작을 단정할 수 없다. 손상, 불완전한 복사, 정상적인 파일 갱신, 비교 대상 착오도 확인해야 한다.

해시가 같아도 파일 내용의 진실성, 수집의 적법성, 실제 작성자까지 증명하지는 않는다.

### 계산 대상 확인

일반 파일의 해시는 보통 파일 내용의 바이트를 대상으로 한다. 파일명, 경로, 파일 시스템의 시각 정보는 일반적인 파일 내용 해시에 포함되지 않는다.

```text
파일명 변경 + 내용 유지 -> 파일 내용 해시는 유지될 수 있음
파일 내부 데이터 변경 -> 파일 내용 해시는 일반적으로 달라짐
```

이미지 컨테이너의 해시와 컨테이너 안에 담긴 디스크 데이터의 해시도 구분한다. 계산 범위가 다르면 값을 직접 비교할 수 없다.

## 해시 알고리즘의 종류

보고서에서 해시 알고리즘과 해시 값을 각각 입력하는 이유는 어떤 계산 방법으로 얻은 값인지 구분하기 위해서다. MD5, SHA-1, SHA-256, SHA-512는 서로 다른 알고리즘이므로 같은 파일을 계산해도 값과 출력 길이가 달라진다.

| 알고리즘 | 출력 길이 | 16진수 길이 | 특징 |
| --- | --- | --- | --- |
| MD5 | 128비트 | 32자리 | 충돌 공격이 알려져 있어 의도적인 변조에 대한 검증 근거로 단독 의존하기 어렵다 |
| SHA-1 | 160비트 | 40자리 | 충돌 저항성이 깨져 새로운 보안 용도의 선택으로 적절하지 않다 |
| SHA-256 | 256비트 | 64자리 | SHA-2 계열이며 증거 내용의 무결성 확인에 활용할 수 있다 |
| SHA-512 | 512비트 | 128자리 | SHA-2 계열이며 SHA-256보다 긴 출력을 제공한다 |

SHA 계열의 출력 길이와 보안 특성은 [NIST 해시 함수 자료](https://csrc.nist.gov/projects/hash-functions)에 정리되어 있다. MD5의 보안 한계는 [RFC 6151](https://www.rfc-editor.org/rfc/rfc6151)에서 설명한다.

과거 보고서나 도구에는 MD5와 SHA-1이 남아 있을 수 있다. 기존 자료와의 비교용으로 값을 유지하더라도 새로 확보하는 자료에는 SHA-256 같은 충돌 저항성을 갖춘 알고리즘을 함께 기록하는 방식이 적절하다.

무결성 확인에서도 의도적인 조작 가능성을 고려해야 하므로, 암호학적 보안성을 무시해도 된다고 볼 수는 없다. MD5와 SHA-1을 함께 계산하는 것이 SHA-256의 대체가 되는 것도 아니다.

## Windows에서 해시 계산하기

### certutil

사진에 나온 명령의 기본 형태는 다음과 같다. [Microsoft 공식 문서](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/certutil#-hashfile)는 `-hashfile` 옵션을 파일 해시를 생성하는 기능으로 설명한다.

```text
certutil -hashfile <파일 경로> <해시 알고리즘>
```

실제 명령에서는 꺾쇠 괄호를 제외하고 파일 경로와 알고리즘을 입력한다.

```powershell
certutil -hashfile "C:\Forensics\evidence\sample.bin" SHA256
```

경로에 공백이 있으면 따옴표로 감싼다. 파일 크기가 크면 계산에 시간이 걸릴 수 있다.

기존 보고서에 MD5나 SHA-1만 기록되어 있다면, 같은 알고리즘으로 값을 계산해 비교할 수 있다.

```powershell
# 기존 기록과 비교하기 위한 값
certutil -hashfile "C:\Forensics\evidence\sample.bin" MD5
certutil -hashfile "C:\Forensics\evidence\sample.bin" SHA1

# 함께 기록할 SHA-256 값
certutil -hashfile "C:\Forensics\evidence\sample.bin" SHA256
```

`SHA-256`의 명령어 인자는 하이픈 없는 `SHA256`이다. `SHA-1`도 명령에서는 `SHA1`로 입력한다.

기존 값과의 일치는 기존 기록에 대한 비교 결과이고, 나중에 계산한 SHA-256이 과거 수집 시점의 무결성을 소급해서 보장하지는 않는다. 최초 확보 시점부터 알고리즘과 값을 기록해야 한다.

### PowerShell

```powershell
Get-FileHash -LiteralPath 'C:\Forensics\evidence\sample.bin' -Algorithm SHA256
```

두 파일을 비교할 때는 다음처럼 각각 계산한다.

```powershell
$evidencePath = 'C:\Forensics\evidence\sample.bin'
$copyPath = 'C:\Forensics\analysis\sample.bin'

$evidenceHash = Get-FileHash -LiteralPath $evidencePath -Algorithm SHA256 -ErrorAction Stop
$copyHash = Get-FileHash -LiteralPath $copyPath -Algorithm SHA256 -ErrorAction Stop

if ($evidenceHash.Hash -ne $copyHash.Hash) {
    throw '해시 불일치: 비교 대상과 복사 과정을 확인하세요.'
}

Write-Output '해시 일치: 파일 내용의 동일성을 확인했습니다.'
```

이 명령은 이미 존재하는 파일의 해시를 계산한다. 디스크 이미징이나 증거 수집을 대신하지 않는다.

| 항목 | 기록 내용 |
| --- | --- |
| 증거 식별자 | 사건 내에서 구분할 수 있는 고유 번호 |
| 출처와 수집 경위 | 장치·계정·서비스, 수집 권한과 범위 |
| 수집 정보 | 담당자, 시작·종료 시각, 시간대, 방법 |
| 계산 대상 | 파일 경로, 크기, 이미지 또는 데이터 범위 |
| 해시 정보 | 알고리즘, 전체 해시 값, 계산 시각 |
| 보존·관리 기록 | 보관 위치, 접근과 전달 내역 |
| 분석 환경 | 도구와 버전, 설정, 분석 절차 |
| 검증 결과 | 비교 대상, 일치 여부, 오류와 한계 |

보고서에는 결론과 함께 수집 경로, 보존·관리 기록, 사용 도구, 분석 절차와 검증 결과를 제시한다.

---

## 정리

디지털 증거는 쉽게 복제되고 변경되며, 일부는 빠르게 사라진다.

적법한 수집, 원본 보존, 해시 검증, 관리 이력, 재현 가능한 분석이 증거의 신뢰성을 뒷받침한다.

해시는 내용의 동일성을 검증하는 중요한 수단이지만, 증거의 출처와 수집 절차까지 대신하지는 않는다.
